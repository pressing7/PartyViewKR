# PartyViewKR 구조 정리 계획

기준: 0.3.60.0, 2026-11-06. **웹 제거와 인게임 네 탭 배치, AFK 파티원 참가 알림과 참가한 파티의 모집 조회·알림은 적용했다. Discord에서 모집 관리·생성·탐색·참가까지 제공하는 것이 확정한 목표이며, 내부 구조와 Discord의 새 화면·기능은 후속 제안이다. 생성·탐색·참가는 아직 구현하지 않았다.**

## 목표와 이번 변경 범위

PartyViewKR의 목표는 **인게임 파티찾기 창에서 하는 주요 작업을 Discord에서 끝낼 수 있게 하는 것**이다. 현재 제공하는 내 모집글 조회·수정·갱신에 더해 새 파티 모집 생성, 모집 목록 탐색, 다른 모집 상세 확인과 참가를 포함한다. AFK 자동 관리와 채팅도 함께 제공한다.

Discord를 모바일에서 독립적으로 조작 가능한 화면으로 설계한다. 모집을 살펴보고 선택하고 실행한 뒤 결과를 확인하는 과정까지 Discord 안에서 이어져야 한다. 인게임 화면도 같은 처리 규칙을 사용하며 초기 연결 설정·진단·직접 조작을 제공한다. 실제 게임 작업은 실행 중인 게임 PC와 플러그인이 수행한다.

0.3.57에서 로컬 HTTP 서버, 브라우저 화면, Cloudflare 중계 클라이언트·Worker, 접속 키·주소 설정, 전용 테스트와 빌드 파일을 제거했다. Discord가 사용하던 공유 요청 큐는 `ListingBridge`, 표시 모델은 `ListingViewProjection`과 `Remote*`, 변경 요청 검증은 `ListingEditContract`로 이름을 정리했다. 웹 상태 응답을 위해 매번 만들던 직렬화 버퍼도 제거했다.

0.3.58에서는 인게임 화면을 디스코드 → 자동화 → 설정 → 디버그 순서의 네 탭으로 나눴다. 각 탭의 표시 코드를 별도 `PartyWindow` partial 파일로 분리했으며, 요청 처리·저장 설정·Discord 카드·게임 조작은 기존 경로를 유지한다. 0.3.59에서는 자동화 탭에 선택형 파티원 참가 알림을 추가했다. 기존 AFK 명단에서 참가 인원을 관측하고, Discord 알림 담당부가 지정 채널의 everyone 멘션을 보낸다. 0.3.60에서는 조회·알림 대상을 현재 참가한 파티까지 확장했다. 현재 소속과 파티장·응답 대상을 확인하는 공통 읽기 검증을 추가하고 편집·갱신은 본인 전용으로 유지한다.

설정의 공개 타입 이름 `RelayConfiguration`은 기존 Dalamud 설정 파일의 타입 정보를 읽기 위해 유지한다. 이 이름을 유지하는 것이 중계 기능을 남긴다는 뜻은 아니다. `ServerUrl`만 제거하고 암호화 토큰, 자동 연결 여부, 채팅 채널·멘션, 알림 채널, AFK 설정을 보존한다. 이후 설정 모델을 나눌 때는 먼저 명시적인 이전 절차를 준비한다.

Cloudflare에 이미 배포한 Worker나 계정은 이번 소스 변경으로 삭제되지 않는다. GitHub Actions와 릴리스 발행은 사용자가 실행한다.

## 기능 범위와 현재 상태

| 작업 | Discord에서 할 수 있게 할 일 | 현재 상태 |
| --- | --- | --- |
| 내 모집 관리 | 본인 모집 조회, 소개말·직업 제한·조건 편집, 수동 갱신, 결과 확인, 수정창 복구 | 기존 기능 유지·구조 정리 대상 |

| 새 모집 생성 | 콘텐츠·파티 유형·구성·조건·소개말 작성 후 모집 시작, 생성 결과 확인 | 후속 구현 |
| 모집 탐색 | 모집 목록 조회, 검색·조건 선택, 페이지 이동 | 후속 구현 |
| 다른 모집 확인 | 아직 참가하지 않은 모집을 목록에서 선택해 상세·조건·자리 확인, 목록으로 복귀 | 후속 구현. 현재 참가한 파티의 조회와 구분 |
| 모집 참가 | 선택한 모집에 참가, 필요한 입력 처리, 참가 결과 확인 | 후속 구현 |
| 자동화·채팅 | AFK 조회·갱신·알림과 종류별 채팅 수신·전송 | 기존 기능 유지. Discord에서 제공할 설정 화면은 별도로 정리 |

게임의 각 목록 필드·필터·생성 옵션·참가 방식은 실제 조회와 UI 이벤트 경로를 확인하며 구현한다. 목표 범위에 포함됐다는 사실과 현재 한섭에서 읽고 조작할 수 있다고 검증된 범위는 구분한다.

## 현재 복잡해진 이유

| 현재 상태 | 사용자와 유지보수에 미치는 영향 |
| --- | --- |
| 모집·개별 편집·AFK·진단·연결을 한 흐름에 표시하던 `PartyWindow.Draw` | 0.3.58에서 네 탭으로 분리했다. 새 UI는 소유 영역에 추가한다. |
| `Plugin`의 여러 partial이 UI 요청, 초안, 설정 저장, 게임 실행을 연결 | 새 기능마다 같은 파일군에 조건과 상태가 더해진다. |
| 인게임 초안과 Discord 편집 세션의 입력 경로가 다름 | 항목 배치, 지원 조건, 문구가 따로 바뀌기 쉽다. |
| 수동 조회·수정, AFK 조회·갱신, 수정창 닫기의 작업 소유권이 여러 위치에 있음 | 앞으로 목록·상세 조회와 생성·참가까지 추가되면 같은 게임 창을 사용하는 작업의 충돌 규칙이 더 중요해진다. |
| 상태와 실패 이유가 UI 문자열·상태 문자열·진단 코드에 나뉨 | 사용자 결과와 개발 진단의 표현이 어긋나기 쉽다. |

이미 검증된 native UI 조작과 상태 기계는 재사용한다. 정리는 화면과 책임의 경계를 분명히 하는 작업으로 시작하고, 파일 이동만으로 끝내지 않는다.

## 인게임 화면 — 0.3.58 적용

주 화면은 아래 순서의 네 탭으로 나눈다. 처음 열리는 탭은 **디스코드**다. 탭마다 독립적으로 스크롤하며 상단 탭은 계속 보인다. 연결 상태는 디스코드, AFK 실행 상태와 알림 전달 상태는 자동화, 채팅 전달 상태는 설정에서 확인한다.

| 탭 | 보여줄 내용 | 주 동작 |
| --- | --- | --- |
| 디스코드 | 개인 봇 연결 상태, 토큰 저장·삭제, 초대·설정 안내, 이모지 준비 상태 | 연결 켜기/끄기, 토큰 변경 |
| 자동화 | AFK 모드, 명단 변화 시 조회, 선택형 주기 조회·갱신, 실패 조회 재시도, 모집 완료 알림 | AFK 켜기/끄기, 옵션·주기 설정, 다음 갱신까지의 상태와 최근 자동 처리 결과 확인 |
| 설정 | 파티·연합·귓속말 채팅의 수신 여부·멘션 조건·수신 채널·전달 상태 | 종류별 수신·멘션 설정. 채널은 기존 Discord 명령과 같은 저장값 사용 |
| 디버그 | 현재 모집글과 등록 직업, 현재 파티의 실시간 정보, 상세 진단, 수동 이벤트 추적 | 내 모집 조회·수정·갱신, 정보 다시 읽기, 진단 표시·복사, 기록 시작/종료 |

인게임에서는 게임 자체로 가능한 모집 조회·수정·갱신을 디버그에 모아 플러그인이 받은 정보와 실행 결과를 확인한다. 모집의 자리 표시는 모집창에 등록된 직업과 자리 제한을 기준으로 하며, 현재 파티의 실시간 직업은 별도 구역에 둔다. 편집 모달은 탭의 ID·스크롤 영역 밖에서 그려, 요청 후 탭이 바뀌어도 초안 표시·닫기를 처리한다. 탭 이동만으로 조회·갱신·연결이나 추적 기록을 실행하지 않는다. AFK 밖에서 명단 지속 감시를 새로 켜는 것은 이 변경에 포함하지 않는다.

## 모집 편집의 공통 구성

인게임과 Discord는 동일한 항목 정의와 순서를 사용한다. 플랫폼에 맞는 입력 방식은 유지한다.

새 모집의 **콘텐츠·파티 유형·모집 구성** 선택과 기존 모집의 조건 편집을 구분한다. 아래 항목의 표시·입력·검증 정의는 재사용하되, 신규 작성 초안과 기존 모집 원본에 묶인 수정 초안은 별도로 관리한다. 기존 모집에서 콘텐츠·파티 유형을 바꾸는 기능의 지원 범위는 해당 게임 동작을 확인한 뒤 정한다.

| 구역 | 항목 |
| --- | --- |
| 목적 | 모집 목적, 초행 및 초보자 환영 |
| 모집 역할 | 자리별 허용 직업, 잡 중복 없음 |
| 모집 참가 조건 | 완료 조건, 평균 아이템 레벨 |
| 임무 찾기 설정 | 제한 해제, 최저 아이템 레벨로 참가, 초월하는 힘 무효화, 전리품 규칙 |
| 모집 범위 | 비공개 여부와 네 자리 비밀번호 |
| 소개말 | 소개말 입력 |

기존 모집의 조건 변경은 공통 변경 목록에 모아 한 번의 **적용 및 갱신**으로 처리한다. Discord에서는 목적 옆의 **수정** 버튼으로 조건 입력을 열고, 소개말·비공개·자리 직업은 기존의 별도 입력 흐름을 유지한다. 변경 취소 전용 버튼은 새로 추가하지 않는다.

조회와 갱신은 명확히 구분한다. **조회**는 정보를 다시 받아오고, **갱신**은 기존 조건으로 시간을 갱신하며, **적용 및 갱신**은 선택한 변경을 반영한다. 자동 갱신이 미적용 편집값을 가져가서는 안 된다.

**모집 시작**과 **참가**도 각각 독립된 요청이다. 생성에서는 새 초안을 제출하고 생성된 본인 모집을 확인한다. 참가는 선택한 모집의 identity와 현재 참여 상태를 다시 확인한 뒤 실행하고 실제 참가 결과를 확인한다. 기존 갱신의 Create 모드 차단은 유지하고, 생성에는 별도의 실행 경로를 만든다.

콘텐츠별 조건은 현재 게임에서 확인 가능한 상태를 기준으로 활성화한다. 인원수·잠금 콘텐츠·제한 해제 가능 여부·서버 초월 허용 여부를 UI마다 별도 목록으로 하드코딩하지 않는다. 기존 수정에서 지원 불가 항목을 건너뛰는 정책을 필수 콘텐츠나 구성 정보가 빠진 신규 생성에 그대로 적용하지 않는다. 실제로 생성할 조건을 Discord에서 알 수 있게 한다.

## Discord 탐색 구조 제안

`/pvkr`는 파티찾기 홈을 열고, 다음 세 경로를 제공한다. 자동화·채팅 설정은 공통 메뉴로 접근한다. 홈은 현재 연결·참여·모집 상태와 진행 중인 작업을 요약한다.

| 경로 | 화면 흐름 | 핵심 동작 |
| --- | --- | --- |
| 내 모집 | 내 모집 조회 카드 → 별도 편집·직업 상세·전체 결과 카드 | 조회 / 갱신 / 수정 |
| 파티 찾기 | 검색·조건과 모집 목록 → 선택한 모집 상세 → 참가 결과 | 목록 다시 조회 / 이전·다음 페이지 / 상세 / 참가 |
| 새 모집 | 콘텐츠·파티 유형·구성 선택 → 조건·소개말·직업 작성 → 작성 내용과 결과 확인 | 모집 시작 |

목록에서 상세로 갔다 돌아오면 검색 조건과 페이지를 유지한다. 내 모집 정보와 다른 모집 상세는 서로 다른 상태로 보관해, 다른 모집을 살펴봤다는 이유로 내 편집 원본을 바꾸지 않는다. 다른 모집 상세의 동작은 참가 중심으로 구성하며 본인 전용 수정·갱신 버튼을 붙이지 않는다.

참가 대상은 목록의 몇 번째 행인지가 아니라 검증된 모집 식별 정보에 연결한다. 버튼을 누르기 전 사이 모집이 종료되거나 정원이 차거나 조건이 바뀌면 실제 확인된 결과를 안내한다. 확인할 수 없는 참가 조건은 가능하다고 단정하지 않고 게임의 결과를 전달한다. 필요한 비밀번호 등의 입력도 Discord에서 처리한다.

## Discord 화면 원칙

- 내 모집 조회 카드는 위쪽에 조회·갱신·수정, 자리 영역에 직업 상세를 둔다. 조회 카드에 자리 수정·상태 확인 버튼을 다시 늘리지 않는다.
- 등록 자리의 이모지를 파티별로 모두 표시하고, 전체 직업 제한은 별도 상세 카드로 읽는다. 24·48인과 친선경기의 실제 물리 자리 매핑을 보존한다.
- 비활성 모집 조건은 조회 카드에서 숨긴다. 활성 조건은 소개말 위에 묶고 비공개·초보자 환영은 콘텐츠 이름 앞 아이콘으로 표시한다.
- 수정은 별도 카드에서 진행한다. 주의 문구와 반복적인 켜기/끄기 버튼을 다시 추가하지 않는다.
- 최근 결과는 성공·건너뜀·실패·미확인을 구분한다. 길면 페이지로 나누되 전체 내용을 유지하고, 게임 화면을 보라는 이유로 생략하지 않는다.
- 채팅은 종류별 색상과 `닉네임@서버 : 내용`을 유지한다. 조회 카드의 수명과 채팅 기록을 연결하지 않는다.
- 카드 만료 방식 변경은 별도 합의 항목으로 둔다. 이번 구조 정리에서 자동으로 영구 카드로 바꾸지 않는다.

## 내부 책임 분리 제안

아래는 폴더·모듈의 목표다. 한 번에 모두 옮기지 않고 동작을 보존하며 한 경로씩 분리한다.

| 영역 | 맡을 책임 | 현재 코드에서 재사용할 부분 |
| --- | --- | --- |
| 시작과 종료 | 서비스 생성·연결·구독 해제·종료 | `Plugin`의 수명 관리 |
| 파티찾기 작업 | 목록·상세·본인 조회, 기존 수정·갱신·생성·참가·창 닫기를 각각 처리. 공통 실행 순서·소유권·결과 관리 | 기존 관리에는 `ListingBridge`, `ListingPendingChanges`, `ListingRefresh`, `ListingBatchRefresh` 재사용. 목록·생성·참가 처리기는 후속 추가 |
| 모델과 검증 | 목록 요약, 모집 상세, 내 모집 편집 원본, 신규 모집 초안, 현재 참여 상태를 구분. 자리·조건·변경값의 공통 검증 | `ListingSlots`, `ListingJobRules`, 각 `Edit`, identity·role normalization. 필요한 모델을 단계적으로 추가 |
| 게임 연동 | Framework에서 읽기·UI 이벤트·native 호환 검사. 게임 창을 공유하는 각 동작의 검증된 경로 제공 | `ListingReader`, `PartyRosterReader`, 각 `*EditHost`, `NativeCompatibility`. 목록·생성·참가 경로는 별도 조사 |
| 자동화 | AFK 명단 변화, 주기와 재시도 예약, 완료 조건 관측 | `AfkListingMonitor`, `AfkRefreshScheduler`, 완료 판정 |
| 채팅과 알림 | 채팅 수신·전송·답장 대상, 전달 경로·멘션 정책, 완료 알림 | `GameChatCapture`, 채팅 전송 큐, Discord 채팅·알림 처리 |
| 화면과 Discord | 사용자 입력을 요청으로 변환하고 공통 상태·결과 표시 | `PartyWindow`, `ListingDiscordPanel`, `ListingDiscordSession`, Discord 전송부 |
| 설정과 진단 | 기존 설정 이전·저장, 비밀값 보호, 상태 기록·진단 내보내기 | `RelayConfiguration`, 설정 저장 함수, 진단 출력 |

화면 코드는 게임 포인터를 읽거나 직접 UI 이벤트를 보내지 않는다. Discord 네트워크 콜백과 자동화 타이머도 실행 요청만 만들고, 실제 게임 조작은 Framework에서 처리한다.

각 작업은 전용 처리기를 두고, 실행 조정은 공통으로 한다. 조회·수정·갱신·생성·참가는 각각 독립된 실행 상태와 결과 검증을 가진다. 모든 작업은 출처·요청 ID·대상·캐릭터·실행 상태를 연결하고, 게임 창을 공유하는 동작은 한 번에 하나씩 실행한다. 이미 받은 관리형 목록이나 결과 페이지를 읽는 일은 게임 UI 조작과 구분한다.

수동 탐색·생성·참가·편집이 게임 창을 쓰는 동안 자동 조회·갱신을 미룬다. 내 모집 갱신을 위한 상세 조회가 다른 모집의 참가 대상을 바꿔서는 안 된다. 오래된 자동 작업을 쌓아 나중에 연속 실행하지 않는다. 연결 종료는 해당 연결이 시작한 작업만 중단하고, 뒤에 시작한 인게임 작업을 취소하지 않는다. 수정창 닫기는 진행 중인 자기 모집 작업을 중단하고 확인된 모집 관련 창만 닫는다. 생성·참가도 불확실한 네트워크 응답을 이유로 자동 재실행하지 않는다.

현재 `ListingBridge`에는 과거 HTTP에서 쓰던 숫자 상태값과 JSON 변경 요청 형식이 일부 남아 있지만 웹 수신 기능은 없다. 공통 처리부를 정리하는 단계에서 typed 요청·결과로 교체하고, Discord 표시 변환은 별도 어댑터로 둔다. 이 교체를 웹 제거와 동시에 진행하지 않는다.

## 반드시 보존할 동작

| 항목 | 보존할 기준 |
| --- | --- |
| 직업 정보 | 현재 착용 직업으로 모집 등록 직업을 덮지 않는다. AFK 명단 변화는 CID로 비교한다. |
| 자리 | 표시 순번과 native index를 구분하고 미등록·친선 5+5+8 padding을 보존한다. |
| 일부 변경 불가 | 콘텐츠가 막은 조건은 결과를 남기고 가능한 변경·갱신을 계속한다. 본인·모집 identity 상실이나 잘못된 창은 계속 제출하지 않는다. |
| 결과 확인 | 제출 시도, 내용 반영 확인, 시간 초기화 확인을 구분한다. 불확실한 갱신을 자동 재제출하지 않는다. |
| AFK | 본인·참가 파티의 명단 변화 조회와 알림은 AFK에서 실행. 수정·자동 갱신은 본인 모집만 허용한다. 주기 조회·갱신은 각각 선택형 1~55분. 실패 조회 재시도는 별도 옵션과 대기 시간 유지. |
| 모집 완료 | 전체 완료는 기억한 정원과 현재 명단으로 관측한다. 모집 종료로 상세 조회가 불가능해져도 알림을 막지 않는다. 단일 직업 공석 제외 조건은 검증된 자리 정보로 판정한다. |
| 채팅 | AFK와 무관하게 종류별 수신·멘션 설정을 따른다. 효과음 멘션, 동일 서버 이름 보완, 개인 답장 제약을 보존한다. |
| 설정 | 토큰·이모지를 재등록하게 만들지 않는다. 자동화 옵션은 저장하되 AFK 활성 상태는 재시작 때 자동 복원하지 않는다. |
| 오류 안내 | 사용자 결과와 상세 진단을 분리하고, 사용자 결과 전체를 외부에서도 읽을 수 있게 한다. |

## 진행 순서와 완료 기준

1. **웹 제거 — 0.3.57 적용**: 웹 실행 경로·화면·배포 자료 제거, Discord 공유 코드 유지, 기존 설정 복원·전체 회귀 검사. 구조 제안과 코드 지도 갱신.
2. **인게임 화면 — 0.3.58 적용**: 디스코드·자동화·설정·디버그 네 탭과 영역별 파일 분리. 기존 조작·설정은 보존한다. Discord의 내 모집·파티 찾기·새 모집 흐름과 새 편집·결과 화면은 후속 합의 대상이다.
3. **공통 처리부 정리**: 인게임·Discord·자동화가 같은 요청·변경 목록·결과 규칙을 사용하게 기존 관리 경로부터 전환한다. 본인 모집과 탐색 대상, 신규 작성 상태를 분리할 경계를 준비하고 기존 네이티브 편집 상태 기계를 재사용한다.
4. **설정·자동화·채팅 책임 분리**: 기존 설정 이전 검사를 갖춘 뒤 나눈다. 동시 실행, 로그아웃, 지역 이동, 연결 재시작, 수정창 복구의 기존 동작을 확인한다.
5. **기존 동작 확인**: 일반 4·8인, 미등록 포함 24·48인, 친선경기, 부분 실패, 자동 갱신, Discord 재접속·채팅을 확인한다.
6. **파티찾기 기능 확장**: 권장 순서는 목록·다른 모집 상세 조회 → 참가 → 새 모집 생성이다. 먼저 조회 대상과 목록 상태를 검증한 뒤 참가 결과 확인을 연결하고, 생성은 콘텐츠·파티 유형별 조건을 확인하며 확장한다. 기능별 우선순위와 세부 입력 방식은 구현 전에 합의한다. 각 단계에서 Discord 화면까지 함께 완성한다.

각 단계는 소스 검토와 관련 테스트를 통과한 뒤 사용자 인게임 확인을 받는다. 빌드·manifest 버전과 코드 지도를 같이 갱신하며, Actions 실행과 배포는 사용자가 맡는다.

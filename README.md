# PartyViewKR

한섭 파티원·모집글 조회, **내 모집글 수동 갱신 및 제한 해제·최저 아이템 레벨로 참가·초월하는 힘 무효화·전리품 규칙·평균 아이템 레벨·완료조건·비공개·비밀번호·잡 중복 없음·초보자 환영·목적·소개말·빈자리 허용 직업 수정** 플러그인입니다. `/pvkr`로 엽니다.
같은 PC의 브라우저에서 내 모집글·등록된 직업·모집 조건을 조회할 수 있습니다. 콘텐츠·파티 유형 등 전체 조건의 편집과 새 모집 시작은 이후 단계입니다.

## 설치와 업데이트

Dalamud 설정 → 실험적 기능 → 사용자 지정 플러그인 저장소에 다음 주소를 추가합니다.

```
https://raw.githubusercontent.com/pressing7/PartyViewKR/main/pluginmaster.json
```

플러그인 설치기에서 **Party View KR**을 설치하거나 업데이트합니다.
배포 파일은 [Releases](https://github.com/pressing7/PartyViewKR/releases)의 `PartyViewKR.zip`입니다.
저장소 루트에 남아 있는 이전 수동 업로드 DLL/JSON은 최신 배포 파일이 아닙니다.

## 0.3.31의 같은 PC 브라우저 조회

1. 게임에서 `/pvkr`를 열고 **브라우저 조회**를 펼칩니다.
2. **브라우저 조회 켜기 → 접속 링크 복사**를 누릅니다.
3. 같은 PC의 브라우저 주소창에 붙여넣습니다.
4. 웹 화면의 **내 모집글 조회**를 누르면 기존 조회 경로로 게임의 모집 상세창을 열고 결과를 표시합니다.

웹 화면은 본인으로 확인된 모집글, 소개말, 등록된 직업·허용 직업, 모집 목적과 조건을 표시합니다. 현재 파티원의 실시간 직업으로 바꾸지 않습니다. 연합파티는 A~F, 친선경기는 별빛팀·그림자팀·관전으로 나누며 미등록 칸을 제외한 실제 자리 번호를 유지합니다. 허용 직업은 기존 순서대로 마우스오버 또는 펼치기로 확인합니다. 상세창이 닫히거나 연결이 끊기면 마지막 조회 결과임을 표시하고 남은 시간을 임의로 카운트다운하지 않습니다.

페이지를 여는 것과 화면의 주기적 읽기는 저장된 표시 정보만 가져옵니다. 게임에 새 조회를 보내는 것은 **내 모집글 조회** 버튼뿐입니다. HTTP 스레드에서는 게임 메모리나 UI에 접근하지 않고, 대기 요청을 게임의 `Framework.Update`에서 처리합니다. 수정창·편집 팝업·갱신 작업 중에는 조회를 막고 실행 직전에도 상태를 다시 확인합니다. 같은 요청의 중복 실행, 오래 대기한 요청의 뒤늦은 실행, 자동 재시도를 막습니다. 로그아웃·캐릭터 변경 때 이전 화면과 대기 요청을 비웁니다.

브라우저 연결은 기본적으로 꺼져 있고, 켤 때 `127.0.0.1`의 빈 포트와 임의의 접속 키를 새로 만듭니다. 끄거나 플러그인을 종료하면 연결과 대기 중인 웹 조회를 정리합니다. 다시 켰다면 새 링크를 복사해야 합니다. 키는 URL의 fragment에서 읽은 뒤 주소창에서 제거하고 브라우저 탭의 세션 저장소에 보관합니다. API 인증과 Host·Origin 검사를 적용하며, 진단 원문·캐릭터 Content ID·모집 비밀번호·대기 중인 수정값을 웹 응답에 포함하지 않습니다. 화면 파일은 DLL에 포함되어 별도 웹 서버 설치나 추가 런타임 DLL이 필요하지 않습니다.

이번 버전의 연결 범위는 **같은 PC의 조회**입니다. 브라우저 갱신·일괄 수정과 집 밖 휴대폰 연결은 다음 단계입니다. 이 로컬 접속 주소를 공유하거나 외부에 포트 포워딩하는 방식으로 확장하지 않습니다.

관리 코드 테스트 **279개**, 배포 도구 테스트 **10개**, 로컬 Release 빌드로 검증했습니다. 실제 TCP 연결에서 인증·잘못된 접속 주소·조회 요청·종료를 확인했고, 4·8·24·48인/친선경기와 캐릭터 변경·중복 요청·시간 초과를 검사했습니다. 조회 접수와 실제 게임 실행 사이에 캐릭터·편집 상태가 달라지는 경우와, 웹 조회를 끄면서 다른 로컬 조회를 취소하지 않는지도 검사합니다. 현재 작업 환경은 Chromium 다운로드가 실패해 실제 브라우저 렌더링 검증은 실행하지 못했습니다. **Windows 브라우저 및 게임 안에서의 연결 확인과 Actions 빌드·배포는 사용자가 실행합니다.**

선택적으로 Playwright/Chromium이 준비된 개발 환경에서는 관리 코드 테스트를 빌드한 뒤 `node tests/browser-smoke.cjs`로 가짜 게임 상태와 실제 로컬 서버를 연결해 화면을 검사할 수 있습니다. `PVKR_DOTNET`으로 dotnet 경로를, `PVKR_BROWSER_ARTIFACTS`로 화면 캡처 저장 폴더를 지정합니다. 이 테스트 도구는 배포 DLL에 포함되지 않습니다.

## 0.3.30의 일괄 수정 오류 복구 보완

소개말 입력은 화면에 반영됐지만 게임에 저장되지 않은 경우, 해당 항목을 마치면서 입력창을 실제 저장된 소개말에 맞춘 뒤 다음 수정을 진행합니다. 실패한 소개말 콜백을 다시 보내거나 다른 조건을 되돌리지 않습니다. 정리 입력도 한 번만 보내며, 작업이 남긴 입력과 다른 수동 입력이나 바뀐 수정창은 덮어쓰지 않습니다.

변경 목록은 내 모집글 조회와 실행 전 확인이 끝날 때까지 보관합니다. 이미 열린 수정창·조회 실패·실행 전 취소로 중단되어도 입력한 변경은 남습니다. 게임 수정창을 여는 요청을 시작할 때 해당 실행의 항목만 목록에서 제거하므로, 이미 적용됐을 수 있는 변경을 자동으로 재시도하지 않습니다. 캐릭터 변경·로그아웃 때 목록을 비우는 동작은 유지합니다.

구조 DLL 호환성 검사에 숫자 입력·드롭다운 선택·이벤트 기록에서 사용하는 이벤트 번호 6개를 추가했습니다. 단순 DLL 버전 변경은 기존처럼 허용하고, 실제 사용하는 이벤트 번호가 달라진 경우에는 비호환으로 판정합니다. Actions 빌드·배포와 실제 게임 확인은 사용자가 실행합니다.

관리 코드 테스트 **256개**, 배포 도구 테스트 **10개**, 로컬 Release 빌드(경고·오류 0)를 통과했습니다. 네이티브 검사 1,088개 항목은 빌드용 `7.57.0.9378`과 제공된 `7.57.0.9700` DLL 모두 차이 0입니다. 실제 입력창 동작과 갱신 후 반영은 인게임에서 확인해야 합니다.

## 0.3.29의 일괄 수정과 부분 실패 처리

각 수정 팝업의 **변경 목록에 저장**으로 소개말·목적·여러 자리의 허용 직업·체크박스·규칙 변경을 모읍니다. 메인 창의 **변경사항 적용 및 갱신 (N)**을 한 번 누르면 내 모집글을 다시 확인하고, 수정창을 한 번 열어 순서대로 적용한 뒤 한 번 갱신합니다. 대기 목록이 없으면 기존 수동 갱신으로 동작합니다. 같은 항목을 다시 저장하면 마지막 선택으로 대체하며, 팝업을 다시 열어 실제 모집글의 원래 값으로 저장하면 그 항목은 대기 목록에서 빠집니다. 대기 값은 현재 등록된 값과 구분해 표시하고, 직업 목록은 마우스오버로 확인합니다.

콘텐츠에서 비활성화된 설정, 항목별 읽기·적용·검증 실패, 제한 시간 초과는 해당 항목의 오류로 기록하고 다음 변경을 계속합니다. 모두 실패해도 게임 수정창에 남은 조건으로 갱신을 한 번 요청합니다. 중간에 일부만 반영된 값도 다음 항목 전에 다시 읽으므로 성공한 변경을 이전 값으로 덮어쓰지 않습니다. 직접 메모리를 수정하지 않고 기존 UI 입력·이벤트 경로를 사용합니다. 직업 선택창이나 드롭다운을 열어 둔 채 실패한 경우에는 해당 작업이 연 창만 닫아 다음 항목을 진행합니다.

갱신 후 내 모집글을 다시 조회하여 **항목마다 실제 반영 여부**를 표시합니다. 수정창에서 성공했어도 서버 조회값이 다르면 미반영이며, 중간 검증에 실패했어도 최종 조회값이 일치하면 반영으로 표시합니다. 미반영·확인 필요 항목에는 사유를 표시하므로 실제 모집 정보에서 다시 수정할 수 있습니다. 비밀번호는 모집글에서 조회할 수 없으므로 네 자리 입력 검증과 수정창 확인을 따로 유지하며, 실패한 비밀번호 입력을 비공개 표시만 보고 성공으로 판단하지 않습니다. `0000`도 허용하고 비밀번호를 진단이나 대기 목록에 노출하지 않습니다.

캐릭터 변경·로그아웃·지역 이동·구조 DLL 비호환·본인 수정창 소실처럼 갱신 대상을 조작할 수 없거나, 게임의 확인창/갱신 버튼 자체가 막힌 경우에는 실제 갱신이 불가능하므로 그 상태를 안내합니다. 일괄 수정 시작 전 다른 모집글이나 참가자 변경이 확인되면 오래된 편집을 적용하지 않습니다. 자동 재시도나 중복 갱신은 하지 않습니다.

로컬 Release 빌드는 경고·오류 0, 관리 코드 테스트 **244개**를 통과했습니다. 모든 설정과 여러 직업 자리의 누적 적용, 부분/전체 실패 후 갱신, 예외·시간 초과, 서버 결과 불일치, 비밀번호 확인 한계, 친선경기 5·4·8의 내부 자리와 미등록 칸을 검사했습니다. 실패한 직업 선택창 정리에 사용하는 `AtkUnitBase.Close(bool)`를 구조 검사에 추가했으며 사용자 제공 7.57.0.9700 DLL에서 **1,082개 구조 항목 차이 0**을 확인했습니다. **인게임 검증은 필요하며 Actions 빌드·배포는 사용자가 실행합니다.**

인게임에서는 소개말 + 여러 빈자리 직업 + 적용 가능한 설정 + 현재 콘텐츠에서 선택 불가능한 설정을 함께 저장한 뒤 갱신합니다. 게임 수정창이 한 번만 열리는지, 가능한 변경이 반영되는지, 마지막에 실제 모집글과 미반영 사유가 표시되는지 확인합니다.

## 0.3.28의 친선경기 수정창 값 비교 수정

사용자의 0.3.27 기록에서 친선경기 **17자리(별빛 5 / 그림자 4 / 관전 8)**의 실제 모집 자리는 모두 일치했습니다. 차이는 친선경기에서 사용하지 않는 두 팀의 6~8번, 내부 인덱스 `5,6,7,13,14,15`에만 있었습니다. 이 여섯 칸은 모집글에서 `0`, 수정창에서 `00000000FDFFFFFE`였고, 별도로 미등록한 그림자팀 5번(인덱스 12)은 양쪽 모두 `0`이었습니다.

| 자리 | 모집글 값 | 수정창 값 | 비교 처리 |
| --- | --- | --- | --- |
| 별빛·그림자 6~8번의 고정 미사용 칸 | `0` | `00000000FDFFFFFE` | 친선경기 구성 확인 후 이 차이만 허용 |
| 실제 미등록한 그림자 5번 | `0` | `0` | 여전히 정확히 일치해야 함 |
| 참가자·빈자리·관전석 | 기존 직업 제한 값 | 기존 직업 제한 값 | 여전히 정확히 일치해야 함 |

수정창에 들어갈 때와 갱신 제출 전에 이 규칙을 공통 적용합니다. 실제 게임 배열이나 모집글 기대값을 덮어쓰지 않습니다. 직업 수정 중에는 선택한 자리 외의 전체 원시 값이 수정 시작 때와 같은지 기존 검사로 확인하고, 다른 설정 편집 중에도 전체 직업 제한을 보존합니다. 갱신 후 새 모집글은 기존처럼 미사용 여섯 칸이 `0`인 상태로 비교합니다. 일반·24인·48인 구성, 다른 미등록 칸, 다른 직업 제한 값이나 알 수 없는 비트는 이 예외에 포함하지 않습니다.

진단의 `editorRoleCheck=mismatch`는 두 원시 배열이 다름을 계속 보여 줍니다. 확인된 여섯 칸의 차이만 있는 경우 `editorRoleCriteriaMatch=True`, `editorRolePaddingAcceptedIndices=5,6,7,13,14,15`가 함께 출력됩니다. 해당 칸은 `kind=unused_friendly_padding`으로 구분합니다.

사용자가 제공한 배열을 재현한 검사와 실제 자리·추가 미등록 칸·다른 설정의 변경을 거부하는 검사를 포함해 관리 코드 테스트 **229개**가 통과했습니다. 로컬 Release 빌드도 경고·오류 0입니다. **실제 게임에서는 같은 자리의 직업 수정과 갱신 후 재조회까지 확인해야 합니다. Actions 빌드·배포는 사용자가 실행합니다.**

## 0.3.27의 친선경기 직업 제한 비교 진단

사용자는 0.3.26에서 미등록 칸이 있는 24·48인 유형의 설정 변경이 가능함을 확인했습니다. 친선경기는 수정창을 연 직후 `stored_criteria_mismatch; draftDifferentFields=roles`로 멈췄으며, 직업 선택창 열기·직업 클릭·갱신 제출은 실행되지 않았습니다. 이 기록만으로는 서로 다른 자리와 실제 수정창 값을 알 수 없어, **0.3.27은 비교 진단을 추가하는 버전이며 친선경기 수정 완료 버전은 아닙니다.**

수정창 검증에 실제로 사용한 예상값과 수정창 값을 `editorRoleExpectedFlags` / `editorRoleDraftFlags`로 보존합니다. `editorRoleDifferenceIndex` 행은 다른 자리의 내부 인덱스, 표시 순번, 그룹·파티원 번호, 참가 중·빈자리·미등록 구분, 두 원시 값과 차이 비트, 현재 직업 목록에서 추가·제외된 직업 ID를 보여 줍니다. `knownJobsAgree=True`라도 알 수 없는 비트의 의미까지 같다고 판단하지 않으며 기존 전체 값 비교를 유지합니다. 진단에는 캐릭터·모집글 ID, 소개말이나 비밀번호를 포함하지 않습니다.

빌드 후 같은 친선경기 빈자리의 직업 수정을 한 번 시도하고, 멈춘 직후 PVKR 진단을 복사합니다. `refreshNativeCheck`와 `editorRole`로 시작하는 행들을 함께 확인하면 됩니다. 상세 창이 이미 닫혔더라도 검증 당시 값은 다음 수정 시도 전까지 남습니다. 이 자료로 참가자 자리, 미등록 자리, 실제 직업 제한, 알 수 없는 비트 중 어디에서 차이가 발생하는지 구분한 뒤 처리 규칙을 정합니다.

로컬 Release 빌드(경고·오류 0)와 관리 코드 테스트 **222개**를 통과했습니다. 추가 테스트는 그룹 사이 미등록 칸과 마지막 관전석의 인덱스, 직업 비트 해석, 잘못된 배열 길이, 기록 보존 및 개인정보 미출력을 확인합니다. 게임 이벤트·콜백과 구조 DLL 요구 항목은 추가하지 않았습니다. Actions 빌드·배포는 사용자가 실행합니다.

## 0.3.26의 미등록 자리 처리와 친선경기 편집 보완

**각 파티 뒤쪽의 미등록 칸을 생략하고, 조회된 팀·자리 번호로 표시하고 수정합니다.** 사용자가 확인한 것처럼 생성 전에 B파티 1번을 미등록으로 지정해도, 생성 후에는 B파티 8번이 미등록으로 정리됩니다. 최초 클릭 위치를 기억해서 적용하지 않고 매번 새 모집글의 실제 배치를 읽습니다.

이전에는 등록 인원이 정확히 24명·48명이어야 연합파티로 편집할 수 있었고, 참가자 배열도 등록 인원수만큼 앞에서 잘라 비교했습니다. 이제 3그룹은 내부 24칸, 6그룹은 48칸을 읽고, 직업·참가자·허용 직업 값이 모두 없는 미등록 칸을 구분합니다. 표시 순번과 내부 자리 번호를 별도로 유지해 다음 파티의 자리나 뒤쪽 관전석이 잘리지 않도록 했습니다. 단일 파티의 기존 조회 범위는 유지합니다.

| 조회된 구성 | 표시 및 편집 기준 |

| 별빛 5 / 그림자 5 / 관전 8 | 별빛 1~5, 그림자 1~5, 관전 1~8을 모두 표시 |
| A 8 / B 7 / C 8 | B 8은 생략하고 C 1~8 유지; C 1은 내부 인덱스 16 |
| 48인 유형 중 한 파티가 7명 | 총 47자리여도 6그룹으로 처리하고 뒤쪽 파티·자리 번호 유지 |

일반 연합파티도 미등록 6칸이 있으면 총 18자리가 될 수 있으므로 인원수만으로 친선경기를 판정하지 않습니다. 친선경기 명칭과 직업 버튼 처리에는 사용자 기록의 참가 조건 값 `0x13` 중 `0x10` 표시와 5·5·8 범위를 함께 확인합니다. 해당 비트의 의미는 아직 구조 DLL에 명명되지 않았으므로, 자리 조회 자체는 이 판정에 의존하지 않습니다.

조회·수정 전·갱신 후에 동일한 내부 인덱스로 자리와 참가자를 비교합니다. 다른 사람이 들어오거나 게임에서 미등록 칸을 복원해 배치가 바뀌면 이전 편집 내용을 적용하지 않고 재조회를 요구합니다. 진단에는 `listingRegisteredSlotCount`, `listingUnregisteredSlotCount`, `listingUnregisteredNativeIndices`, `listingSlotMappingValid`, `listingCategoryRaw`를 추가했습니다.

로컬 Release 빌드(경고·오류 0), 관리 코드 테스트 **219개**, 배포 도구 테스트 **10개**를 통과했습니다. 구조·상호운용 검사 **1,083개**는 빌드 참조와 사용자 제공 DLL 모두 차이가 없습니다. 추가 테스트는 파티별 뒤쪽 미등록 칸, 전체 관전석 조회, 다음 파티의 편집 대상, 각 설정의 갱신 흐름과 배치 보존을 검증합니다. **실제 게임 동작은 아직 확인이 필요하며, Actions 빌드·배포는 사용자가 직접 실행합니다.**

## 0.3.21의 비공개 설정과 비밀번호

**내 모집글 조회 → 비공개 설정 → 체크 및 비밀번호 입력 → 변경 적용 및 갱신**으로 사용합니다.

- 비공개를 켤 때는 ASCII 숫자 **네 자리**를 입력해야 합니다. `0123`처럼 앞에 0이 있는 입력도 유지하며, 게임에는 해당 숫자 값으로 전달합니다. 기존 비밀번호는 상세 조회에 없으므로 미리 채우지 않습니다.
- 이미 비공개인 모집에서는 비밀번호만 바꿀 수 있습니다. 비공개를 끌 때는 비밀번호 입력이 필요 없습니다.
- 0.3.21에서는 구조체 주석의 `Password=0` 미설정 설명을 근거로 `0000`을 제한했습니다. **0.3.22에서 사용자의 한섭 입력 기록에 따라 이 제한을 제거했습니다.** `10000`은 공개 상태로 구분하며 실제 입력창의 허용 범위도 확인합니다.

수동 기록에서 체크박스는 **ButtonClick(25), Param 29 → 명령 21의 UInt 1/0**, 비밀번호는 **ValueUpdate(27), Param 29 → 명령 16의 Int 값**으로 확인했습니다. 앞자리 0이 있는 입력은 숫자로 전달됐습니다. 중간의 명령 15는 소개말 입력과 관련된 이벤트이므로 비밀번호 처리에 사용하지 않습니다.

PVKR은 실제 체크박스와 숫자 입력 컨트롤의 소유 노드·등록된 이벤트 연결을 확인합니다. 체크박스는 기존 토글과 같이 `SetChecked` 및 등록된 클릭 이벤트를 한 번 처리합니다. 비밀번호는 [숫자 입력 API](https://github.com/aers/FFXIVClientStructs/blob/main/FFXIVClientStructs/FFXIV/Component/GUI/AtkComponentNumericInput.cs)의 `InnerSetValue(value, triggerCallback: true, playSoundEffect: false)`를 한 번 호출하며, 값 변경 이벤트와 콜백은 게임이 생성합니다. 명령 16/21을 직접 생성하거나 모집 정보의 Password 필드에 값을 쓰지 않습니다.

비공개 체크 상태, 숫자 입력값, 저장된 비밀번호가 요청과 일치하고 갱신 버튼이 활성화된 뒤 제출합니다. 비공개 해제는 체크 해제와 공개 상태 저장값이 일치해야 합니다. 그동안 소개말·목적·초보자 환영·잡 중복 없음·전체 자리와 참가자를 비롯한 나머지 조건이 바뀌면 중단합니다. 실패한 입력을 다시 보내지 않습니다.

갱신 후 새로 조회한 상세에서 **비공개 여부와 다른 조건 유지**를 확인합니다. 상세에는 비밀번호가 없으므로 서버에 등록된 비밀번호까지 재조회했다고 표시하지 않습니다. 진단의 `privatePasswordUiMatches/StoredMatches`는 제출 전 입력·저장 일치 여부이고, `privatePasswordServerCheck=unavailable`은 서버 비밀번호를 읽지 못한다는 뜻입니다. 일반 진단과 수동 기록에는 비밀번호 숫자를 출력하지 않습니다.

로컬 빌드와 관리 코드 테스트를 통과했고, 이전 구조체 검사 985개를 유지한 채 숫자 입력 관련 79개를 추가했습니다. **실제 게임에서는 공개→비공개, 비공개 상태에서 비밀번호 변경(앞자리 0 포함), 비공개→공개를 확인해야 합니다.** 실제 비밀번호로 참가할 수 있는지도 확인해 주세요. Actions 빌드·배포는 사용자가 직접 실행합니다.

## 0.3.20의 잡 중복 없음 설정

- 갱신 후에는 새 모집 상세의 `JoinConditionFlags.OnePlayerPerJob` 비트(`0x20`)로 확인합니다. 다른 참여 조건 비트, 목적·초보자 환영·소개말·자리와 참가자는 그대로 비교합니다. 기존 977개 호환 검사 항목은 유지하고 참여 조건 열거형 8개 항목을 추가했습니다.
- 일반 4·8인 및 연합 24·48인의 기존 모집을 대상으로 합니다. 게임에서 체크박스가 숨겨져 있거나 비활성화되어 있으면 변경하지 않습니다. 창 변경·캐릭터 변경·실패·시간 초과 시 재클릭하지 않습니다.

진단에는 `listingJoinConditionFlags`, `listingUniqueJobs`, `refreshUniqueJobsEdit`, `uniqueJobsEditCheck/Phase`, `uniqueJobsCheckCalls/ClickCalls`, `uniqueJobsUiChecked`, `uniqueJobsStoredValue`, `uniqueJobsNode/Param`, `uniqueJobsResultExpected/Actual/ContentsAgree`가 추가됩니다. 기존 초보자 환영과 공통 체크 상태 검증을 사용하며, 목적·소개말·직업 수정 경로는 유지합니다.

## 0.3.19의 초행 및 초보자 환영 설정

모집 상세의 `BeginnerFriendly`를 읽어 **초행 및 초보자 환영: 켬/끔**을 표시합니다. 알 수 없는 값은 꺼짐으로 간주하지 않고 **확인 불가**로 표시합니다.

1. **내 모집글 조회 → 초보자 환영 설정**을 엽니다. 현재 상태로 체크박스를 채웁니다.
2. 켜거나 끈 뒤 **변경 적용 및 갱신**을 누릅니다. 상태가 같으면 적용 버튼은 비활성화됩니다.
3. 최신 내 모집글을 확인한 뒤 게임 수정창의 체크박스를 한 번 처리합니다. 화면 체크 상태와 저장값이 요청과 일치하면 갱신하고, 새로 조회한 모집글에서도 결과를 확인합니다.

사용자가 제공한 스크린샷과 수동 켜기·끄기 기록에서 `BeginnersWelcomeCheckBox` **노드 17 / ButtonClick(25) / Param 21 / 수신자 모집 수정창**을 확인했습니다. 게임이 생성한 콜백은 켤 때 `18 / 0 / 1`, 끌 때 `19 / 0 / 1`이었습니다. PVKR은 체크박스의 `SetChecked(원하는 상태)`와 실제 등록된 클릭 이벤트를 사용하며, 이 콜백을 직접 만들거나 모집 설정 메모리에 값을 쓰지 않습니다. 기록의 `checked`/`storedValue`는 목적 드롭다운의 값이었으므로 초보자 환영 확인에 사용하지 않습니다.

일반 4·8인 및 연합 24·48인의 기존 모집에서 지원합니다. 본인 여부, 새 조회 응답, 수정창 연결과 갱신 모드를 확인합니다. 목적·소개말·직업 제한·참가자와 나머지 조건이 바뀌면 중단합니다. 화면만 바뀌고 저장값이 반영되지 않으면 갱신하지 않으며, 실패한 클릭을 다시 보내거나 다른 방식으로 재시도하지 않습니다.

진단에 `listingBeginnerRaw/Readable`, `refreshBeginnerEdit`, `beginnerEditCheck/Phase`, `beginnerCheckCalls/ClickCalls`, `beginnerUiChecked`, `beginnerStoredValue`, `beginnerResultExpected/Actual/ContentsAgree`를 추가했습니다. `beginnerDirectCallbackCalls=0`은 PVKR이 초보자 환영 콜백을 직접 생성하지 않는다는 뜻입니다. 전후 표시 시간이 모두 60분인 경우 설정 반영 확인과 시간 초기화 확인을 구분합니다.

**0.3.19 사용자 기록에서 초보자 환영 끄기의 체크 상태·저장값·재조회 결과가 일치했습니다. 기존 목적 수정도 0.3.18 사용자 기록에서 요청값과 재조회 값이 일치했습니다. Actions 빌드·배포는 사용자가 직접 실행합니다.**

## 0.3.18의 게임 드롭다운을 통한 목적 수정

0.3.17에서 받은 한섭 수동 선택 기록으로 목적 드롭다운의 이벤트 경로를 확인했습니다. **내 모집글 조회 → 목적 수정 → 항목 선택 → 변경 적용 및 갱신**을 다시 사용할 수 있습니다.

| 단계 | 기록에서 확인한 이벤트 | 수신 대상 |
| --- | --- | --- |

기록에서 마지막 단계의 게임 내부 콜백 인자는 화면 순번 0/1/2/3에 대해 각각 `Int 20 / UInt 1·2·3·4 / UInt 0`이었고 저장값은 1/2/4/8로 바뀌었습니다. `callbackReturned=False`는 네 경우 모두 나타났으므로 실패 판정으로 사용하지 않습니다. 0.3.16의 매핑은 이 기록으로 확인됐지만, **이번 구현은 게임 UI의 선택 경로를 사용하며 목적 콜백을 직접 만들지 않습니다.**

- 확인된 노드 16(드롭다운), 내부 노드 2(체크박스), 내부 노드 3(목록)과 실제 등록 이벤트의 대상·수신자·Param을 확인합니다.

- 게임 목록의 `DispatchItemEvent(index, ListItemClick)`으로 항목 클릭을 전달하고, 수동 기록대로 목록이 닫혔으나 기존 선택값이 남아 있는지 확인합니다. 같은 업데이트 안에서 `SelectItem(index, true)`를 한 번 호출해 화면 선택과 선택 이벤트를 함께 처리합니다. 이후 목적 콜백은 게임이 생성합니다.
- **화면 순번·목록 순번·저장된 목적값이 모두 요청과 일치하고 목록 전환이 끝난 뒤** 갱신합니다. 기존처럼 다른 조건·새싹 설정·소개말·전체 48자리와 참가자를 보존하는 검사와 갱신 후 재조회 검증을 유지합니다.
- 열림 실패, 예상과 다른 클릭 결과, 다른 목적값, 화면만 바뀐 상태, 창 변경 등에서는 중단합니다. 다른 방식으로 재시도하거나 모집 목적 메모리에 직접 쓰지 않습니다.

진단에는 `objectiveEditPhase`, `objectiveOpenCalls`, `objectiveItemClickCalls`, `objectiveSelectCalls`, `objectiveUiIndex`, `objectiveListIndex`, `objectiveStoredValue`, `objectiveDropdownOpen/Pending`가 들어갑니다. `objectiveDirectCallbackCalls=0`은 PVKR이 목적 콜백을 직접 호출하지 않는다는 뜻입니다. 선택 이후의 게임 내부 호출과 구별합니다.

상태 전환 테스트는 수동 기록의 네 변경(1→2→4→8→1), 목록 열림 실패, 화면/저장값 한쪽만 바뀐 경우, 전환 중인 목록, 다른 목적, 동작 재시도 방지를 확인합니다. [FFXIVClientStructs의 목록 API](https://github.com/aers/FFXIVClientStructs/blob/main/FFXIVClientStructs/FFXIV/Component/GUI/AtkComponentList.cs)와 제공된 한섭 DLL에서 새로 사용하는 함수와 가상 함수 슬롯을 확인하고 호환 검사에 추가했습니다.

**수동 이벤트 경로는 인게임 기록으로 확인했으며, 이를 연결한 자동 동작은 이번 빌드로 인게임 확인이 필요합니다. Actions 빌드·배포는 사용자가 직접 실행합니다.**

## 0.3.17의 목적 선택 진단

목적은 게임 드롭다운을 열고 항목을 선택하는 경로로 구현할 예정입니다. 그 경로를 확인하기 위해 0.3.17에서는 **수동 조작 기록**을 추가했습니다. 기록 기능은 0.3.18에도 유지합니다. 0.3.15/16의 `FireCallback(20, 선택값, 0)` 호출과 추정한 `+1` 변환은 제거했습니다. 0.3.17에서는 목적 자동 수정 버튼을 잠시 비활성화했으며, 0.3.18에서는 기록에 따라 UI 경로로 다시 연결했습니다. 기존 모집 갱신·소개말·직업 수정은 유지합니다.

1. 게임에서 **현재 모집의 수정창**을 직접 엽니다. 목적 드롭다운은 닫힌 상태로 둡니다.
2. `/pvkr` 하단의 **목적 선택 진단 → 목적 기록 시작**을 누릅니다.
3. 게임 드롭다운에서 **설정 안 함 → 완료 목적 → 연습 → 반복 공략 → 설정 안 함** 순서로 고릅니다. 각 항목에서 잠깐 기다린 뒤 다음 항목을 선택합니다. 마지막 설정 안 함은 첫 선택이 이미 설정 안 함이어서 이벤트가 생략되는 경우를 대비합니다.
4. PVKR에서 **기록 종료 → 목적 기록 복사**를 누르고 내용을 전달합니다. 모집 갱신 버튼을 누를 필요는 없습니다. 기록 후 게임 수정창을 닫으면 됩니다.

기록에는 드롭다운·체크박스·목록의 노드와 등록 이벤트, 실제 `ReceiveEvent`의 타입·Param·목록 선택 번호, 선택 전후 화면 번호·내부 목적값·열림 상태가 들어갑니다. 같은 수정창에서 실제 `FireCallback` 호출이 발생하면 인자 타입과 숫자/불리언 값도 기록합니다. 문자열·포인터의 내용은 읽지 않습니다. `pre#N`/`post#N`은 같은 호출의 앞뒤이며 중첩 호출 순서를 유지합니다.

기록은 명시적으로 시작한 동안에만 활성화하며, 게임의 원래 호출에 인자를 바꾸지 않고 한 번 전달합니다. 이벤트 생성·목적 선택·메모리 쓰기·모집 제출은 수행하지 않습니다. 기록 중에는 PVKR의 다른 조회·갱신·편집 요청을 막아 수동 동작과 섞이지 않도록 합니다. 최대 2분 또는 1,024줄에서 종료하고, 수정창 닫힘·로그아웃·캐릭터 변경·창 포인터 변경·플러그인 종료에도 해제합니다. 이전 기록은 복사할 수 있도록 유지하고 다음 기록 시작 시 교체합니다.

[Dalamud의 훅 안내](https://dalamud.dev/plugin-development/interaction/expanding-game-events/) 및 [FFXIVClientStructs의 이벤트 정의](https://github.com/aers/FFXIVClientStructs/blob/main/FFXIVClientStructs/FFXIV/Component/GUI/AtkEvent.cs)를 참고했습니다. 사용자가 제공한 구조 DLL에서 드롭다운·이벤트 데이터·네이티브 델리게이트 정의를 확인하고 호환 검사에 포함했습니다.

**로컬 빌드와 관리 코드 테스트는 게임의 이벤트 경로를 증명하지 않습니다. 0.3.17은 경로 확인용 버전이었으며, 받은 기록에 따른 자동 선택은 위 0.3.18에 연결했습니다. Actions 빌드·배포는 사용자가 직접 실행합니다.**

## 0.3.14의 소개말 최종 전달 수정

0.3.13 인게임 보고에서 수정창의 표시와 임시 저장값은 요청한 5글자였지만, 갱신 후 조회한 소개말은 3글자로 남았습니다. 사용자가 갱신 버튼을 직접 눌러도 같은 현상이 있었습니다. 따라서 수정창의 값이 일치하는 것만으로 최종 등록 요청에도 같은 문자열이 전달된다고 볼 수 없습니다.

제공된 PFRemote 1.0.0.12를 다시 확인하면 `CreatePf b__0`의 명령 15 이후, 최종 `CreatePf b__1`에서도 `FireLfgCommand(addon, 0, comment)`로 소개말을 전달합니다. 0.3.13은 이 최종 문자열 전달 대신 기존의 갱신 버튼 클릭 경로를 사용했습니다.

- 소개말 수정은 최종 제출에도 새 문자열을 포함하여 `FireCallback(3, values, true)`로 명령 0을 한 번 전달합니다. 빈 문자열도 생략하지 않고 전달합니다.
- 본인 모집글과 수정창 연결, **모집 내용 갱신** 모드, 소개말·참가자·다른 조건의 최종 검사를 모두 통과해야 제출합니다. 새 모집 화면에서는 실행하지 않습니다.
- 일반 갱신과 직업 수정의 버튼 클릭 경로는 유지합니다. 실패 시 다른 제출 경로로 재시도하지 않습니다.
- 진단에 `descriptionSubmitCallbackCalls`, `descriptionSubmitCallbackReturned`와 재조회한 소개말의 일치 여부·기대/실제 글자 수·다른 조건과 자리의 일치 여부를 추가했습니다. 콜백 반환값만으로 성공을 판단하지 않고 재조회 결과를 확인합니다.
- 소개말 반영은 확인했지만 전후 표시 시간이 같을 때에는 소개말 확인과 남은 시간 초기화 확인을 구분하여 안내합니다.

**사용자가 0.3.14에서 소개말 변경을 인게임 확인했습니다. 빈 소개말로 되돌리기는 별도 확인이 필요합니다. Actions 빌드·배포는 사용자가 직접 실행합니다.**

## 0.3.13의 소개말 편집

소개말을 별도의 테두리 영역에서 줄바꿈하여 보여주고, 내 모집글에는 **소개말 수정** 버튼을 표시합니다.

1. `내 모집글 조회` 후 `소개말 수정`을 누르면 기존 내용이 채워진 넓은 편집창이 열립니다.
2. 소개말을 입력하거나 모두 지웁니다. 입력량을 UTF-8 바이트로 표시하며 한글은 보통 한 글자에 3바이트입니다.
3. `변경 적용 및 갱신`을 누르면 최신 모집글을 확인하고 게임 수정창에 소개말을 반영합니다. 반영된 내용과 나머지 조건이 일치할 때 한 번 갱신한 뒤 재조회합니다.

빈 소개말도 지원합니다. 별도 취소 버튼은 없으며 X로 닫으면 적용하지 않습니다. 변경이 없거나 입력 제한을 넘으면 적용할 수 없습니다. 일반 텍스트를 지원하며, 양 끝 공백은 제거하고 줄바꿈을 통일합니다. 게임이 입력을 제한하거나 다른 내용으로 바꾸면 임의로 잘라 등록하지 않고 중단합니다.

게임의 `CommentTextInput.SetText`로 입력 제한과 형식을 적용하고 결과를 확인합니다. 저장된 소개말이 아직 이전 내용일 때만 제공된 PFRemote 1.0.0.12의 소개말 명령(`FireCallback`, 명령 15)을 한 번 전달합니다. 0.3.13에서 사용한 버튼 클릭 제출은 위 보고에 따라 0.3.14에서 최종 소개말을 함께 전달하는 경로로 수정했습니다. 이 입력에 필요한 구조·함수도 DLL 호환성 검사에 포함했습니다.

일반 4·8인 및 연합 24·48인을 지원합니다. 편집 중 참가자나 모집 조건이 달라지면 적용을 중단하며, 다른 자리의 직업 제한과 파티 구성은 그대로 비교합니다. 진단의 `descriptionEditCheck`, `descriptionInputCalls`, `descriptionCallbackCalls`, `descriptionMaxByte`, `descriptionMaxChar`로 반영 단계를 확인할 수 있습니다. 진단에 소개말 원문은 기록하지 않습니다.

기존 직업 수정은 0.3.12에서 일반·연합 모집 모두 사용자의 인게임 확인을 받았습니다. 소개말 변경은 후속 0.3.14에서 확인했으며, 비우기는 별도 인게임 확인이 필요합니다. **Actions 빌드·배포는 사용자가 직접 실행합니다.**

## 0.3.12의 48인 파티 선택 중단 수정

## 0.3.10의 전체 허용 변경 검증과 처리 속도 수정

0.3.9에서 확인 버튼까지 진행한 뒤, 원래 `누구나 가능`이던 자리만 모집 갱신이 멈춘다는 보고가 있었습니다.
기존 검증은 수정 전 슬롯의 직업 비트 외 값까지 그대로 유지할 것을 요구했습니다. 게임이 수정 후 다른 원시 값을 반환하면 허용 직업이 같아도 중단되는 경로를 회귀 테스트로 재현했습니다.
이 수정 이후 사용자가 일반 파티의 직업 수정이 정상 작동하는 것을 확인했습니다.

- 수정한 자리의 **허용 직업 전체**가 선택값과 일치하는지 확인하고, 게임이 확정한 원시 값을 제출 직전까지 그대로 비교합니다. 해당 값은 메모리에 직접 쓰지 않습니다.
- 갱신 후 조회에서도 수정한 자리의 허용 직업을 비교합니다. 다른 자리의 원시 값, 참가자, 소개말, 콘텐츠 등 나머지 조건은 이전처럼 정확히 일치해야 합니다.
- 수정 시작 전에는 기존 모집 정보를 그대로 비교하여, 그 사이 바뀐 글이나 자리에는 적용하지 않습니다.
- 직업 해제는 원본처럼 한 번의 처리에서 연속 호출합니다. 이전에는 직업 하나마다 약 0.5초의 조회 주기를 기다렸습니다. 이제 초기화 → 제외 직업 일괄 해제 → 확인 단계 사이에만 대기하며, 각 이벤트는 한 번만 호출합니다.

진단에는 `slotOriginalFlags`, `slotRequestedFlags`, `slotKnownJobsMask`, `slotConfirmedFlags`를 추가했습니다.
인게임에서는 전체 허용 → 일부 허용, 일부 허용 → 전체 허용, 일부 허용 → 다른 직업을 비교해 주세요. **Actions 빌드·배포는 사용자가 직접 실행합니다.**

## 빈자리 한 칸 직업 수정

1. `내 모집글 조회` 후 수정할 빈자리의 `누구나 가능` 또는 `직업 제한`을 클릭합니다.
2. 직업 선택창에서 체크박스로 허용 직업을 고릅니다. `전체 선택`, `전체 해제`를 제공하며, 직업을 하나도 선택하지 않거나 기존 조건과 같으면 적용할 수 없습니다.

선택하는 동안에는 게임의 모집 조건을 바꾸지 않습니다. 별도의 변경 취소 버튼은 없으며, 선택창의 X를 누르면 적용하지 않고 닫습니다.
참가 중인 자리는 수정할 수 없습니다. 편집 도중 참가자·등록 직업·모집 조건이 바뀌면 적용을 중단하고 새 정보에서 다시 선택하도록 안내합니다.

직업 수정은 **일반 4·8인 및 연합 24·48인 모집에서 한 자리씩** 지원합니다. 일반 파티는 원본 DLL에서 확인된 자리 클릭 경로, 연합 파티는 위의 그룹·자리 연결을 사용합니다.
PvP 친선전과 인원·파티 구성을 확인하지 못한 모집은 조회만 제공합니다.

툴팁과 선택창의 직업 순서는 다음으로 통일합니다. 게임 데이터에 없는 직업은 생략합니다.

자리 조건이 다르면 `expectedFlags`와 `actualFlags`도 기록합니다. 진단에는 모집자의 Content ID를 넣지 않습니다.

## 0.3.6의 빈자리 허용 직업 표시

- 빈자리는 게임의 모든 전투 클래스·잡을 허용할 때만 **누구나 가능**으로 표시합니다.
- 그 외에는 **직업 제한**으로 표시하며, 마우스를 올리면 허용 직업 이름을 빠짐없이 나열합니다. 역할별 요약은 하지 않고 긴 목록은 줄바꿈합니다.
- 참가 중인 자리에는 모집창에 등록된 직업을 계속 표시합니다.
- 허용 직업은 모집 상세의 `SlotFlags`에서 읽습니다. 직업 이름과 전체 직업의 범위는 실행 중인 게임의 `ClassJob` 시트를 사용합니다. 본인의 직업 해금 여부는 영향을 주지 않습니다.
- 직업 목록을 해석하지 못하면 **직업 조건 확인 불가**, 자리 인원수가 맞지 않으면 **확인 중**으로 표시합니다.

인게임에서는 전체 허용, 직업 하나만 허용, 일부 직업만 허용한 빈자리를 비교해 주세요.
표시는 조회 기능이며, 모집 직업 선택값을 변경하지 않습니다.

## 0.3.5의 모집 직업 조회

`내 모집글 조회`에서 소개말과 함께 자리별 등록 직업을 읽습니다.
모집 상세의 `LastViewedListing.Jobs`를 사용하며, 현재 파티원의 실시간 직업으로 대체하지 않습니다.

- 모집글의 전체 자리 수에 따라 최대 48자리까지 원래 순서로 표시합니다. 빈자리를 제거하거나 파티원 순서로 재정렬하지 않습니다.
- 모집자와 소개말이 상세 UI와 일치할 때만 직업 정보를 함께 표시합니다.
- 등록된 직업, 빈자리, 직업 정보가 없는 참가자를 구분합니다. 인원수와 자리 정보가 어긋나면 확인 중으로 표시합니다.
- 기존 현재 파티 표는 아래쪽의 `현재 파티 상태 · 실시간 직업`에서 펼쳐 볼 수 있습니다.
- 진단에는 직업 ID, 멤버 존재 여부, 자리 조건을 추가합니다. 멤버의 Content ID는 진단에 포함하지 않습니다.
- 이번 단계는 조회 기능입니다. 소개말·모집 직업 변경은 다음 단계입니다.

인게임에서는 모집 상세 창의 직업과 새 표를 비교해 주세요.
파티원이 입장 후 직업을 바꿨을 때에도 새 표가 모집 상세 창에 표시되는 등록 직업과 같은지 확인합니다.
4인·48인 모집의 자리 수와 24인 모집의 순서(A 1–8, B 9–16, C 17–24)는 인게임에서 확인했습니다.
빈자리 허용 직업 표시는 0.3.6에서 추가했으며 인게임에서 확인했습니다.

## 0.3.4의 빈 모집 문구 처리

0.3.3은 상세 창의 별도 문자열 버퍼가 비어 있다고 가정했지만, 실제 한섭에서는 화면과 버퍼 모두 `소개말 없음`을 담고 있었습니다.
실제 모집 내용이 빈 값으로 읽히고 두 UI 문자열이 모두 이 안내 문구와 일치하면, 조회·수정 창 확인·갱신 후 비교에 빈 문자열을 사용합니다.
사용자가 직접 `소개말 없음`이라고 작성했다면 실제 모집 내용도 비어 있지 않으므로 그대로 유지합니다.
내용을 읽지 못한 경우나 일반 모집 문구가 서로 다른 경우, 작성자 ID·이름이 다른 경우는 계속 차단합니다.
빈 문구 안내가 확인되면 진단에 `emptyDescriptionPlaceholder=True`, `uiDescriptionChars=0`, `commentAgrees=True`가 표시됩니다.
자동 테스트에서는 실제 보고된 두 UI 문자열과 빈 모집 내용을 사용해 본인 확인 및 한 번의 갱신 흐름을 확인합니다. 실제 게임 동작은 인게임 확인이 필요합니다.

## 0.3.2의 호환성 검사

기존에는 `FFXIVClientStructs.dll`의 빌드 식별자(MVID)가 다르면 네이티브 기능을 모두 중지했습니다.
이제 최초 조회 시 로드된 DLL의 메타데이터를 한 번 읽어, 실제 사용하는 구조체의 크기·필드 위치·형식,
인라인 배열 길이, 호출 함수 시그니처, 가상 함수 슬롯 및 필요한 열거형 값을 비교합니다.
문자열 포인터를 담는 `InteropGenerator.Runtime.CStringPointer`도 확인합니다.

- 필요한 구조가 같으면 MVID/세부 버전이 달라도 조회와 수동 갱신을 허용합니다.
- API가 바뀌거나 필요한 구조가 다르거나 검사를 완료하지 못하면 네이티브 기능을 중지합니다.
- 런타임에는 인터넷 접속, DLL 다운로드/교체, 자동 재등록을 하지 않습니다.
- 진단의 `nativeCheck=structure_match`가 검사 통과입니다. MVID는 참고 정보로 남깁니다.

이 검사는 플러그인과 로드된 라이브러리 사이의 구조 일치를 확인합니다.
게임 자체의 메모리 배치나 함수 동작까지 증명하는 검사는 아닙니다. 큰 게임 패치 후에는 인게임 확인이 필요합니다.
기존 메모리 접근 검사, 본인 모집글 확인, 갱신 버튼 문구 확인 및 중복 실행 방지는 유지합니다.

## 수동 빌드·배포

Actions → **Build and release** → **Run workflow**에서 직접 실행합니다.
코드 push, PR, 태그 생성만으로는 Actions를 실행하지 않습니다.

- 빌드 확인만 할 때: 원하는 브랜치에서 실행하고 `publish`를 끕니다.
- 릴리스·설치기 업데이트까지 할 때: **main**을 선택하고 `publish`(빌드 성공 후 릴리스와 pluginmaster.json 게시)를 켭니다.

워크플로는 고정 참조 ZIP의 해시와 필요한 구조를 검사하고 회귀 테스트·빌드·패키지 버전 검사를 실행합니다.
`publish`를 선택하면 릴리스 ZIP을 게시하고 공개 다운로드의 해시까지 확인한 뒤 `pluginmaster.json`을 갱신합니다.
소스 버전을 올려도 실제 배포가 성공하기 전까지 설치기 JSON은 이전 배포 버전을 유지합니다.

새 버전을 배포할 때 아래 값을 함께 올립니다.

- `src/PartyViewKR.csproj`: `Version`, `AssemblyVersion`, `FileVersion`
- `src/PartyViewKR.json`: `AssemblyVersion`
- 예: `Version=0.3.10`, 나머지 버전은 `0.3.10.0`

같은 버전의 기존 태그와 배포 파일은 덮어쓰지 않습니다.
실패한 배포를 재시도할 때도 main에서 `publish`를 켜고 수동 실행합니다.
기본 브랜치 보호 규칙이 Actions의 JSON 갱신을 막는 경우 해당 규칙에 맞는 반영 절차가 필요합니다.

## 로컬 빌드

.NET SDK 10 및 Python 3이 필요합니다. 저장소 루트에서 실행합니다.

```sh
python tools/release.py references
python tools/release.py verify
dotnet run --project tests/RefreshTests.csproj -c Release
python -m unittest discover -s tests -p 'test_*.py' -v
dotnet build src/PartyViewKR.csproj -c Release -p:DalamudLibPath="<저장소 절대경로>/.build/references"
python tools/release.py package
```

결과는 `release-output/PartyViewKR.zip`입니다. Dalamud 참조 DLL은 설치 ZIP에 포함하지 않습니다.
직접 받은 한섭 DLL 폴더를 쓰려면 `verify --refs <폴더>`와 `-p:DalamudLibPath=<폴더>`를 사용합니다.

## 다음 Dalamud 패치 대응

단순 빌드 변경이며 필요한 구조가 같으면 플러그인을 다시 배포하지 않아도 됩니다.
호환 검사에서 중지되면 `nativeDifferences`와 새 DLL을 비교하고, 실제 코드/게임 동작을 검증한 뒤 기준을 갱신합니다.
`CompatibilityTool capture`는 검토를 위한 개발 명령이며, CI가 자동 호출하면 안 됩니다.

빌드 참조를 바꿀 때는 고정 URL과 SHA-256을 함께 갱신하고 기존 기준으로 `verify`를 먼저 실행합니다.
검사 실패를 해결하려고 현재 실행 DLL을 새 기준으로 무조건 승인하지 마세요.
